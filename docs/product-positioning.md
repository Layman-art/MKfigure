# MK Figure：产品定位与加速价值

核对日期：2026-09-22。依据当前 0.4.0 代码、项目说明和 2026-09-19 实测；本文是产品方案，不表示以下规划已经实现，也未修改生产功能。

## 建议定位

**为需要反复修改论文方法图的研究者，把视觉草稿变成可以交接、继续编辑和检查的科研图。**

当前最具体的交付价值是原生 PowerPoint 对象与 SVG：标题、变量、箭头、模块可继续修改。长期应竞争的是“从首次想法到验收合格的可编辑成品，总共少花多少人力”，而非生成模型本身或第一次出图耗时。

目标用户优先选经常做方法框架图、机制图、算法流程图的研究生和课题组。一次性配图、海报创意、普通整套演示文稿不应成为首要目标；定量结果图应使用数据绘图工具，避免用图像生成代替真实数据。

## 具体痛点及现有证据

| 重复任务 | 现有产品价值 | 当前边界 |
|---|---|---|
| 导师要求只改一个变量、箭头或模块，原图是 PNG | FigureScene 导出原生 PPT 文字、形状和曲线；实际在 PowerPoint 改标题、公式文字、矩形后保存重开成功 | 并非每个复杂图都能高保真重建；目前没有成熟的内置对象编辑器 |
| 每张图重复说明中文字体、英文和公式字体、是否全矢量 | 统一微软雅黑、Times New Roman、数学变量斜体及组件式公式导出规则 | 字体不随软件分发；模型排版及跨系统字体替换仍会出错 |
| 找参考图、下载版本、上传下一阶段、判断哪张是最终稿 | 需求、参考库、视觉稿版本、复刻、检查、导出在同一个作品中衔接 | 素材库图标尚不能一键插入场景；当前记录不是完整可追踪的科学论断来源系统 |
| 工作台看着正常，PowerPoint 打开后文字换行或重叠 | 同一场景生成预览与导出，提供结构检查和可选模型审查 | 结构通过不等于视觉合格；当前低推理样例在工作台和 PPT 都有公式重叠 |
| 不清楚一次操作花了多少时间、是否又发起了模型调用 | 动作级耗时、模型、推理强度和服务回传 token 已记录；导出已有场景不需要重新推理 | 尚缺明确的 CPU、I/O、云端等待分段计时；token 不是订阅余额或费用 |

上述能力依据 [README](../README.md)、[实际数据流](data-flow.md) 及 [低推理实测](../output/low-reasoning-2026-09-19/review.md)。代码入口为 `src/main/workflow.ts`、`src/core/pptx.ts`、`src/core/svg.ts` 与 `src/shared/types.ts`。

## 为什么不直接使用 ChatGPT

可以直接用，而且一次性探索通常更省事。官方文档已明确支持参考图、图像生成与修改、局部反馈；ChatGPT Work 也能创建、修改和下载演示文稿，使用项目和可复用工作流。不能宣传“GPT 不能改图、不能生成 PPT、没有项目或素材管理”。账户、平台和工作区的实际可用能力会有差异。[官方图像说明](https://learn.chatgpt.com/docs/image-generation)、[文件与演示文稿](https://learn.chatgpt.com/docs/artifacts-viewer)、[ChatGPT 工作方式](https://learn.chatgpt.com/docs/use-chatgpt)

MK Figure 的选择理由应是：用户愿意使用一套固定科研图流程，少重复输入约束，稳定得到同一套对象结构和可检查的导出结果。直接 ChatGPT 也可能通过认真编写的提示词或 skill 达到类似结果，因此公允比较应包含“直接 ChatGPT + 同等科研图指令”，不能只挑未经约束的聊天作对照。

| 更适合直接 ChatGPT | 更适合 MK Figure |
|---|---|
| 先讨论研究内容、尝试各种创意，最终仅需一张图片 | 已明确科研图交付标准，要在 PowerPoint 中持续改字、变量和连线 |
| 任务类型经常变化，希望自由对话组织方法 | 反复做相似图，希望固定字体、导出格式和检查步骤 |
| 已经熟悉 skill/代码工作流，可以自行控制输出与验收 | 不想处理代码、图形 JSON 和重复文件搬运，希望阶段状态清晰 |

如果只是把相同提示词包进几个按钮，长期优势有限。可编辑质量、局部修改稳定性、课题组图形规范的积累，才值得投入。

## 哪些主张现在不能说

- **“生成更快”尚未验证。** 相同远端服务的推理不会因为本机有高端 GPU 自动变快。多核 CPU 可能加速本地导入、排版、渲染和打包，但必须先测这些部分在总耗时中的比例。应报告机器等待时间、用户操作时间及返工时间，分别比较。
- **“高保真且全部可编辑”不能当保证。** 2026-09-19 的样例确有 78 个原生元素、0 位图、无 Office Math，但 ODESolve 公式组件重叠，渐变变成纯色；两次生图请求 2:1，实际得到 3:1。
- **“低推理一样好、Plus 更便宜”没有依据。** 现有实测是 Pro 账户的一张简图，没有高低档位对照，也没有 Plus 配额验证。首次生图约 55 秒，全矢量复刻约 160 秒；不能用这组数据推出所有图或账户的成本和速度。
- **“数据完全留在本地”不成立。** 项目、导出和素材副本本地保存，但本次模型任务所需文本、图片会发送给在线服务。现有数据流更明确，不等于具有额外隐私保证。

## 最值得实现的三个差异化，按优先级

### 1. 公式与导出验收：先做到敢交稿

用本地确定性排版计算公式组件位置、字体度量和间距，减少让模型逐字猜坐标；对标题、数学符号、上下标、箭头关系建立可检查清单。保留当前衬线文字与线条组成的可编辑公式，不默认改成 Office Math 或整块图片。导出后用实际 PowerPoint 渲染复核关键区域，出现重叠或丢字则明确标记，不能只看 JSON 合法性。

验收指标：公式与标签准确率、异常重叠数、关键箭头关系通过率、导出前后换行变化数、修改后保存重开通过率。使用简单流程、双语方法图、密集公式图、复杂信息图四类至少 20 张固定样本；人工检查科学含义，像素差仅辅助。目标建议是已知缺陷样例全部修复、关键文字和公式零遗漏；这是建议门槛，不是当前成绩。

### 2. 局部对象修改与可靠复用：减少整图重做

支持选中某个对象或公式组后修改，并锁定其他对象；颜色、文字、字体、对齐等简单修改在本地完成，语义复杂的修改再请求模型。素材库原生 SVG 可以明确插入场景并保留来源，逐步积累课题组常用设备、模块和样式。当前 `refine` 仍要求返回完整场景，仅在提示词中要求保留正确对象，不能当作已实现的可靠局部编辑。

验收指标：未选中对象的属性变化数必须为 0；常见改字、改色、移动操作的远端调用数为 0；达到用户接受结果的修改轮数、人工操作分钟数以及局部修改相对整图复刻的耗时。先支持这些高频动作，再考虑复杂批量模板系统。

### 3. 可预测的速度与用量：只把算力用在需要的部分

先分段计时，再对本地独立任务使用有上限的工作线程；缓存内容未变化的预览、缩略图和导出中间结果，避免同一图重复解析/排版。多张独立图片或文件可排队并行；单图“识别—排版—检查”有依赖，不应为了用满 CPU 把它盲目拆开。GPU 值得评估的候选是大图渲染或图像处理，不能加速已经发送到云端的模型推理；没有瓶颈证据，不建议先增加 CUDA 等安装负担。

验收指标：本地阶段 p50/p95 耗时、界面卡顿、峰值内存、每份验收合格成品的模型调用数、token 与总耗时。单独比较冷启动和缓存命中，并在相同机器、图、格式和质量门槛下测串行与并行。并发模型请求即使减少等待，也可能增加额度消耗或限流，需要独立报告，不能当作本机 GPU 加速。

## 怎样验证“流程集成确实更省时间”

让至少 5 位目标用户完成相同的三项任务：从资料生成方法图、把现成图转成可编辑图、按导师意见只修改局部。对比 MK Figure 与直接 ChatGPT + 同等指令，交换操作顺序减少学习效应，模型和可用工具条件记录在案。先设共同质量门槛，再计时；未通过的产物记失败或继续累计返工时间，不能仅比较第一次出图。

主要指标是“达到可交付质量所需的人工分钟数”；辅助指标是总等待、输入/上传/下载次数、修改轮数和有效完成率。硬件加速应另外做可重复微基准，避免把网络波动、服务排队或模型随机性归因于 CPU/GPU。

对外可以先说：**把科研图生成、修改、可编辑复刻和检查放在同一个工作台，减少反复说明要求与整理文件。** 完成受控对照后，再用具体结果补充“快多少、在哪些图上、质量是否一致”。
