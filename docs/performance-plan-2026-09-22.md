# MK Figure 加速实测与产品路线

2026-09-22，当前产品 0.4.0。本轮按用户要求只做实测、方案和定位，没有修改生产功能、升级依赖、重打包或调用线上模型。

## 结论

多核 CPU 能提升多份独立任务的吞吐，GPU 已用于图形合成和栅格化。但当前科研图复刻的分钟级等待主要发生在远端模型阶段，不能通过本机增加线程或启用 CUDA 直接消除。先减少不必要的模型往返、整图重建和人工返工，比继续压缩几十毫秒的 PPT 打包更有价值。

建议定位：**让论文里的科研图能够反复修改、可靠交付，并逐步积累课题组自己的图形资产。**

“速度快”应改为可验证的目标：从需求到验收合格的可编辑成品，总共减少多少人工操作和返工时间。当前没有与直接 ChatGPT 的受控对比，不应宣传整体更快或更准确。

## 本机实测

硬件：AMD Ryzen 9 7945HX，16 核 / 32 线程；NVIDIA RTX 4060 Laptop GPU。CPU 基准与图形基准错开执行，每组预热后记录 5 次；不是跨机器性能承诺。

| 工作 | 当前路径 | 隔离实验 | 可以得出的结论 |
|---|---:|---:|---|
| 78 元素真实图导出 PPT | 11.82 ms | 未并行 | 本地文件构建很快 |
| 468 元素真实图导出 PPT | 32.57 ms | 未并行 | 加核不是单图主要提速点 |
| 连续导出 4 份 468 元素图 | 136.96 ms | 两个常驻 worker：90.48 ms | 本次批量吞吐约 1.51 倍，未计 86 ms 线程启动 |
| 1500 元素合成压力图导出 PPT | 100.15 ms | 4 份批量：334.92 → 283.26 ms | 大图可考虑工作线程，但不是核数倍速 |
| 1536×1024 复杂图预览 | 新建窗口：209.7 ms | 复用窗口：81.4 ms | 减少重复建窗与导航有收益 |
| 两份复杂 SVG 交替预览 | 新建窗口：207.1 ms | 复用窗口：69.8 ms | 固定两版本实验通过，不代表每次全新图的收益 |

CPU 表格为原生产函数的 Node 实测，包含 PPT 文件写入，不含 Electron 图像渲染；渲染表格是独立 Electron 进程。以上优化实验尚未接入生产软件。两种并行导出的 slide1.xml 完全一致；同一图形模式下的预览像素一致。

多核会增加总 CPU 使用量，并非免费提速。单次导出只用几十毫秒，新建线程的成本可能超过收益；应该使用小型常驻池及队列，优先保证取消、IPC、界面响应。不能把上述批量 1.51 倍称为整张图的生成/复刻加速比。

对照量级：2026-09-19 的真实在线样例，首次生图 55.44 秒，全矢量复刻 159.95 秒。那是先前的完整操作耗时，包含模型与本地处理；不是本轮同条件分段计时。它与本轮本地处理的毫秒量级差异足以说明优先排查方向，但不宜直接相减并报告精确的“云端占比”。

证据：[CPU 报告](../output/performance-2026-09-22/core/report.md)、[渲染报告](../output/performance-2026-09-22/render/README.md)、[历史在线实测](../output/low-reasoning-2026-09-19/review.md)。

## 多核、GPU 与模型并发分别适合什么

| 技术 | 适合的工作 | 边界与取舍 |
|---|---|---|
| CPU 多核 | 多图导入、缩略图处理、批量校验、PPT 打包和独立文件导出 | 用有限工作线程；Promise.all 只能并发等待，并不会把同一个 JavaScript 计算自动分到多核 |
| GPU 图形加速 | 预览、图像合成、部分光栅化 | 当前已经启用；GPU 输出最终仍需读回和 PNG 编码，静态截图未必更快 |
| 多个模型请求并发 | 多张独立图；未来经验证的分区复刻 | 消耗在线服务能力，不是使用本机 GPU；会受额度、限流和模型延迟影响 |
| 本地 GPU 模型 | 未来可能的 OCR、分割或图像预处理 | 当前未部署，需要额外模型、运行环境、质量验证和跨平台维护；现阶段不优先增加 CUDA 依赖 |

GPU 实际状态：RTX 4060 为 active GPU，合成、光栅化、2D canvas 和多线程 raster 已启用。本次软件渲染对照稍快，但与 GPU 模式像素不同，且只覆盖少量静态图，不能据此全局关闭硬件加速。[Electron 离屏渲染说明](https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering)

单张图不能直接按 CPU 核数切块复刻：不同区域可能各自选字体、比例和图层，跨区箭头、公式和共享标签容易断开。可探索“全局布局清单 → 独立区域有限并发 → 统一坐标与字体 → 跨区核对”，但应先作为实验，记录保真、总 Token、返工轮数，再决定是否产品化。

## 优先级与验收门槛

### 第一阶段：先保证导出完整、公式可读

本轮发现并直接调用生产 renderSvgPng 复现 3 次：请求 3072×2048，实际截取约 2050×1105，再拉伸成目标文件尺寸。四角色块中只保留左上角，其余三个角丢失，且 devicePixelRatio=1，排除 DPI 换算。问题在隐藏窗口尺寸受限后仍截屏拉伸。复杂大图另有首帧空白/重复渲染不一致，尚未单独定位；这些大图速度数据已排除。

应先修复这一 P1 正确性问题，考虑使用与屏幕窗口大小无关的指定像素画布渲染，并验证字体与透明度。不能以 PNG 文件头尺寸正确作为验收。证据：[尺寸记录](../output/performance-2026-09-22/render/production-corners.json)、[错误输出](../output/performance-2026-09-22/render/production-corners-0.png)。

同时解决已知低推理样例的公式重叠。尽量由本地字体度量、公式结构和排版规则决定组件位置，让模型提供内容与关系，减少逐字猜坐标。保持衬线文字与线条的可编辑公式，不默认换为 Office Math。

验收：多种长宽比、4096 像素边长及常用 DPI 下四角/边缘完整，无空白帧、拉伸、丢字；已知 ODESolve 重叠样例通过工作台与 PowerPoint 原生显示复查。未经通过，不用加速数字掩盖质量问题。

### 第二阶段：减少整图重做和人工操作

先支持高频的改字、改色、改字体、移动/对齐对象及公式组，直接修改已有场景，不请求模型。建立稳定对象 ID 和明确的修改范围；模型辅助修改返回局部差异，未涉及对象保持不变。原生 SVG 图标插入场景后继续可编辑，保留来源和课题组样式。

当前软件已有文字编辑、图像修改和完整场景精修，但尚未实现以上可靠的全套对象级编辑/局部差异协议。后者要处理依赖关系和冲突，不能仅在提示词写“其他不变”就算完成。

验收：简单本地编辑的模型调用数为 0；锁定对象属性变化数为 0；保留撤销/原版本；达到相同质量时，局部修改的耗时、Token 和返工次数低于完整重建。模型局部修改仍需实测，暂不承诺倍速。

### 第三阶段：缓存与有界并行

建立内容版本＋输出尺寸＋字体/资产指纹的缓存；同一场景多格式导出复用已验证的公共结果；内容变化立即失效。复用受控离屏渲染窗口，通过队列避免不同任务串图。CPU 池从 1–2 个常驻 worker 起步，按测量决定是否增加，不默认占满 32 线程。

先考虑独立文件任务、不同作品的后台队列，再探索单图分区模型并发。取消、失败、重试、峰值内存、CPU 占用与服务用量都要纳入验收。GPU 继续用于适合的图形工作，优先消除重复处理。

验收：分别记录冷启动、缓存命中和内容更新的 p50/p95；检查图片像素/对象结构/字体与之前等价；统计主线程延迟、峰值内存、每份合格成品的模型调用数和 Token。小样本微基准的当前数字是方向依据，不是发布性能承诺。

## 产品价值如何验证

MK Figure 最值得解决的是：导师要求改一个符号却要重画整图；漂亮的图片难以继续编辑；跨格式后字体与公式错位；参考与版本散落；每次重复说明科研图规范。

已有价值是生成、改图、可编辑复刻、检查、素材库及版本在同一个作品里衔接。未来更强的差异应来自稳定对象结构、局部修改不破坏其他区域、可检查的公式/导出、课题组图标和风格的长期复用。

ChatGPT 本身已支持图像生成/编辑和演示文稿工作流。因此公平比较要用“直接 ChatGPT＋同等科研图指令”，设置相同输入和质量门槛，而不是声称 GPT 不能出 PPT。一次性创意配图可以直接用 GPT；经常按同一规范反复修改并交接可编辑文件，才是本产品更明确的目标。

建议用至少 5 位目标用户、20 张分难度固定图集做对照，交叉操作顺序。主指标为**达到验收合格成品所需的人工分钟数**；辅助看总等待时间、修改轮数、文件搬运次数和合格率。先取得对照数据，再决定能否宣传“更快、更稳”。

更完整的痛点、能力边界及官方来源见 [产品定位方案](product-positioning.md)。本轮没有与直接 GPT 做速度/质量对照，不将集成化自动等同于优势已被证明。
